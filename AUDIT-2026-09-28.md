## 1. Executive summary

The codebase was in better shape than a typical pre-launch MVP: defense-in-depth auth (middleware role gates + per-route `requireApiSession`), server-side pricing everywhere I checked, signature-verified webhooks, timing-safe backup bearer auth, and an idempotent ledger. The audit still found real issues:

## 4. Route audit summary

**Framework (verified sound):** `src/middleware.ts` role-gates `/api/admin` (admin), `/api/provider`, `/api/fleet`, `/api/ads`; everything else under `/api/*` requires a session by default; public surface is an explicit allowlist (`/api/auth`, `/api/health`, `/api/webhooks`, `/api/search`, `/api/listings`, exact paths `/api/ads/events`, `/api/backup/export`, `/api/backup/ping`). All 14 admin routes additionally call `requireApiSession(["admin"])` in-handler. Session `role` is set server-side from the DB in the Auth.js JWT callback — not client-controllable. Signup schema restricts role to `client|provider|fleet_owner` (no self-promotion to admin; admin PATCH blocks self-role-change).

**Classification of all 49 routes:** public-intentional (auth handlers, health, Stripe webhook, search, listings, ad events, backup bearer endpoints) / session-authenticated / role-gated / bearer-token — each verified against the middleware matcher; no route accidentally inherits a public prefix, and no route relies on middleware alone.

**Verified secure by independent re-check:** Stripe webhook fails closed when unconfigured (400 before any processing), verifies `stripe-signature` via `constructEvent`, and is idempotent (audit marker + ledger idempotency keys; failures don't write the marker so Stripe retries). Backup export/ping fail closed without `BACKUP_CRON_SECRET` (503/401) and compare with `crypto.timingSafeEqual` (length-gated). Order detail/cancel/transition/adjustments/evidence are party-scoped via `orderScopeWhere`/`authorizeOrder` + state machine (`performTransition` enforces `TRANSITION_ROLES` and ownership; `dispatched→delivered` is provider/admin-only). Ad checkout price comes from server-side `placement.priceCents`; order checkout-intent amount from server-side `grandTotalCents`; payment status can only be flipped by the webhook.

**Findings not fixed (accepted/documented):**
- Signup returns 409 for existing emails (user enumeration) — accepted trade-off, standard for marketplaces.
- Password policy is min-length 8 only; bcrypt cost 12 — acceptable for MVP; consider breach-corpus screening later.
- `/api/health` discloses `stripe: configured|not_configured` — trivial recon, public by design.
- Public search/listing endpoints return exact `serviceLat`/`serviceLng` — by design (distance filtering); could be fuzzed later.
- Unverified providers can publish `active` listings (only a `verified` badge distinguishes them) — **product decision**, flagged: the verification flow implies a trust gate that isn't enforced.
- Admins can post reviews attributed to the order's client — intentional capability; confirm it's wanted.
- Delivery "photo proof" is honor-based (any `https://` URL or `/uploads/` path; transition only checks row existence, not uploader or file) — design limitation; real attestation needs signed upload tokens.
- `allowDangerousEmailAccountLinking: true` for Google — acceptable (Google verifies email ownership); documented risk.
- CSP `'unsafe-inline'` — residual hardening debt (nonce migration is a larger change).

## 5. Fixes applied (files changed)

1. `package.json` / `package-lock.json` — `next` 15.5.4 → **15.5.26**, `eslint-config-next` → 15.5.26, `next-auth` 5.0.0-beta.29 → **5.0.0-beta.32** (all `--save-exact`).
2. `src/app/api/orders/[id]/route.ts` — provider projection narrowed to `businessName/bio/city/state/verificationStatus/ratingAvg/reviewCount` (+ `id/name/phone`); drops `insurancePolicyNo`, `address`, `zip`, `lat`/`lng`, `contactName`, `verificationNotes`. Frontend only consumed `businessName`.
3. `src/app/api/uploads/route.ts` — extension now derived from **magic-byte detection** (JPEG/PNG/WebP), not the client MIME; per-user rate limit (30/min, 429).
4. `src/lib/rate-limit.ts` — added `UPLOAD_RATE_LIMIT`, `AD_EVENT_RATE_LIMIT`; bucket map capped at 10k entries (oldest evicted).
5. `src/app/api/ads/events/route.ts` — per-IP rate limit (120/min, 429) against stat flooding.
6. `src/app/api/search/route.ts` — sponsored campaigns filtered to `listing: { status: "active" }`.
7. `src/app/api/disputes/[id]/resolve/route.ts` — `refundedRentalCents` now increments **only** when the authorization was actually voided (`refundVoided`); previously it also incremented when Stripe was unconfigured, no intent existed, status was neither captured nor authorized, or the Stripe call threw — drifting the counter above reality and corrupting `issueRentalRefund`'s over-refund guard.
8. `src/app/api/fleet/containers/[id]/route.ts` — PATCH rejects `status: "assigned"` (400); assignment (with its provider-verification gate) only via `POST /api/fleet/assign`.
9. `prisma/seed.ts` — refuses to run unless `DATABASE_URL` looks local/dev or `ALLOW_DEMO_SEED=true` is set (it wipes all rows and creates a documented-password admin).
10. `.gitignore` — `.env*` ignored (was only `.env` + `.env*.local`), `!.env.example` re-allowed.
11. `docs/SECURITY.md` — rate-limit table and upload validation description updated to match the new behavior.

After every fix: `tsc` 0 errors, `lint` 0 errors, `npm test` 34/34, `npm run build` exit 0.

## 6. Launch blockers (need a decision before production)

1. **Distributed rate limiting.** The limiter is in-memory per instance; on Vercel serverless it is trivially bypassed (signup/auth abuse). Needs Upstash Redis (`@upstash/ratelimit`) or equivalent — **not implemented: adding a vendor needs your approval.**
2. **Uploads target `public/uploads` on local disk — unwritable on Vercel** (read-only filesystem except `/tmp`). The evidence-photo flow will 500 in production until this moves to S3-compatible storage with presigned PUTs (the documented upgrade path). Decide: S3 now, or gate the flow.
3. **Missing DB indexes on hot FK columns** (recommendation, §8) — fine to defer, but add before real traffic: `Container(fleetOwnerId)`, `Container(assignedProviderId)`, `Order(listingId)`, `AdCampaign(ownerId)`, plus `Listing(providerId)`, `Order(feeScheduleId)`, `EvidencePhoto(uploadedById)`, `OrderEvent(actorId)`, `Dispute(raisedById)`, `AdCampaign(placementId)`, `LedgerEntry(adInvoiceId)` as a follow-up migration.
4. **Backup secret wiring** — `BACKUP_CRON_SECRET` must be set in Vercel env and mirrored in Apps Script properties; the secret lives only in `~/workspace/.secrets/` (never in the repo). Verify both before enabling the cron.
5. Re-run a normal `npm ci` with scripts on an unrestricted network as final install proof (§2 caveat).

## 7. Accepted risks / residual debt

In-memory limiter (until blocker 1 is resolved); CSP `'unsafe-inline'`; signup email-enumeration 409; exact coordinates on public listings; honor-based delivery photo proof; unverified-provider listings (product decision); admin review capability; Google account-linking fail-open flag (documented); seed script override env var exists by design.

## 8. Recommendations (not blockers)

- Add the FK indexes listed in §6.3 via a tested migration.
- Consider breached-password screening (NIST SP 800-63B) and uniform signup responses if enumeration matters.
- Coarsen public coordinates (e.g. 3-decimal) if hauler-location enumeration becomes a concern.
- Signed upload tokens binding evidence uploads to the uploading user + order, so "delivery photo" means something.
- Rotate `AUTH_SECRET` and review secret hygiene after the React2Shell window (Vercel advisory recommends rotation if the app was online unpatched during Dec 2025 disclosure).
